Sécurisation des interconnexions

INF5244 — Majeure Cybersécurité S9. Coef. 1.5. Prérequis : Réseaux (INF4032) et Sécurisation des réseaux locaux (INF5243). Évaluation : travail de synthèse sur environnement virtualisé + examen Moodle sans documents ni Internet. Objectif : étudier, concevoir et mettre en œuvre une passerelle d'interconnexion réseau sécurisée.

Les 4 blocs du programme

  1. Filtrage et architectures internes — nftables, pare-feu à états, NAT, architectures.
  2. Système de journalisation — définition, sources et formats, politique de journalisation, agrégation.
  3. NetFlow — métrologie et détection par les flux.
  4. Filtrage applicatif — proxy et WAF.

Fil rouge Une passerelle sécurisée, ce n'est pas seulement « un pare-feu » : c'est filtrer (réseau puis applicatif), tracer (journaliser, agréger, détecter) et cloisonner (architecture).

1. Rappels : interconnecter des réseaux

1.1 Routage, plans et protocoles

  • Plan de contrôle (routing plane) : construction de la table de routage (protocoles, annonces). Plan de données (forwarding plane) : commutation effective des paquets (FIB/CEF). Plan de gestion : administration (SSH, SNMP). Ces trois plans doivent être protégés séparément.
  • Routage statique : simple, déterministe, sans risque d'injection ; ingérable à grande échelle.
  • IGP : RIP (vecteur de distance, métrique = sauts, max 15), OSPF (état de liens, aire 0 dorsale, coût), IS-IS, EIGRP.
  • EGP : BGP (TCP 179), routage entre systèmes autonomes (AS), fondé sur la confiance entre pairs.

1.2 TCP/IP côté filtrage

Ce qu'un pare-feu observe

  • IP : adresses source/destination, protocole (1 ICMP, 6 TCP, 17 UDP, 47 GRE, 50 ESP, 51 AH), TTL, drapeaux de fragmentation.
  • TCP : ports, drapeaux SYN ACK FIN RST PSH URG, numéros de séquence, fenêtre, options (MSS, SACK, timestamps).
  • UDP : ports, longueur — aucun état intrinsèque : l'« état » UDP d'un pare-feu est une pseudo-session à minuterie.
  • ICMP : type/code ; les types 3 (unreachable) et 11 (time exceeded) doivent être laissés passer, sous peine de casser la PMTUD.

Établissement et états TCP

Poignée en 3 temps : SYN → SYN/ACK → ACK. Fermeture : FIN/ACK × 2 (ou RST).

États utiles : LISTEN, SYN_SENT, SYN_RECV, ESTABLISHED, FIN_WAIT, TIME_WAIT, CLOSE_WAIT.

SYN flood : saturation de la file des demi-connexions → parade net.ipv4.tcp_syncookies=1, limitation de débit, synproxy de Netfilter.

Fragmentation : utilisée pour contourner les filtres (chevauchement, minuscules fragments) → réassemblage obligatoire côté pare-feu (ct state invalid drop).

Les 4 règles d'or d'une politique de filtrage
  1. Interdiction par défaut (policy drop) puis liste blanche explicite des flux nécessaires.
  2. Spécificité : chaque règle précise source, destination, protocole, port et sens ; jamais any → any.
  3. Ordre : les règles sont évaluées séquentiellement — le plus spécifique d'abord, la règle de rejet en dernier.
  4. Traçabilité : chaque règle est commentée (qui, pourquoi, jusqu'à quand) et les rejets sont journalisés ; revue périodique pour supprimer les règles obsolètes (rule sprawl).

DROP ou REJECT ? DROP ne renvoie rien (le scanner attend le délai d'expiration, l'attaquant est ralenti, mais le diagnostic interne devient pénible) ; REJECT renvoie un ICMP port unreachable ou un RST TCP (comportement « propre », meilleure expérience utilisateur). Usage courant : DROP côté Internet, REJECT côté interne.

ÉtatSignificationUsage typique

FTP : le cas d'école du helper
En FTP actif, le serveur ouvre lui-même la connexion de données depuis le port 20 vers un port dynamique du client → un pare-feu à états sans helper la bloque. En FTP passif, le client ouvre les deux connexions, mais vers un port serveur dynamique. Le module ct helper ftp lit la commande PORT/PASV dans le canal de commande pour autoriser dynamiquement le canal de données en état RELATED. Risque : les helpers analysent du contenu non authentifié — sous nftables ils doivent être déclarés explicitement et restreints à un flux précis (pas d'auto-assignation comme avec iptables).

Réglages sensibles : nf_conntrack_max (taille de la table — sa saturation est un déni de service), nf_conntrack_tcp_timeout_established (souvent 5 jours par défaut : à réduire), tcp_loose (accepter ou non une session déjà en cours).

Ordre de traversée en PREROUTING : raw → conntrack → mangle → nat (DNAT) → décision de routage → mangle → filter.

Limites d'iptables qui ont motivé nftables : quatre outils distincts (iptables, ip6tables, arptables, ebtables), duplication IPv4/IPv6, évaluation linéaire des règles, pas de vraie structure de données, rechargement non atomique, extension du noyau nécessaire pour chaque nouvelle correspondance.

3.4 nftables : le modèle

Depuis Linux 3.13, nftables remplace iptables : une machine virtuelle dans le noyau, un seul outil nft, une syntaxe unifiée. Sur les distributions récentes, iptables est en réalité iptables-nft (une façade).

Familles de tables

  • ip — IPv4
  • ip6 — IPv6
  • inet — IPv4 et IPv6 dans le même jeu de règles (à privilégier)
  • arp — trames ARP
  • bridge — trafic ponté (L2)
  • netdev — au plus près de la carte (hook ingress), idéal pour l'anti-DDoS

Types de chaînes de base

  • filter — accepter/jeter
  • nat — traduction d'adresses (le 1er paquet de la connexion seulement)
  • route — reroutage après modification (équivalent de mangle OUTPUT)

Priorités usuelles : raw −300, mangle −150, dstnat −100, filter 0, security 50, srcnat 100. La plus petite valeur s'exécute en premier.

#!/usr/sbin/nft -f
# /etc/nftables.conf — passerelle : WAN=eth0, LAN=eth1, DMZ=eth2

flush ruleset

table inet filtre {
    # --- Ensembles réutilisables (recherche en O(1), mise à jour à chaud) ---
    set reseaux_lan   { type ipv4_addr; flags interval; elements = { 192.168.10.0/24, 192.168.20.0/24 } }
    set bannis        { type ipv4_addr; flags dynamic, timeout; timeout 1h; }
    set services_pub  { type inet_service; elements = { 80, 443 } }

    chain entree {
        type filter hook input priority filter; policy drop;

        ct state established,related accept
        ct state invalid drop                       # paquets hors session / fragments incohérents
        iif lo accept

        # ICMP indispensable (PMTUD, diagnostic) mais limité en débit
        ip protocol icmp icmp type { echo-request, destination-unreachable, time-exceeded } limit rate 10/second accept
        ip6 nexthdr icmpv6 accept

        # Administration : SSH depuis le réseau d'admin uniquement, anti-force brute
        iifname "eth1" ip saddr 192.168.99.0/24 tcp dport 22 \
            ct state new limit rate 3/minute burst 5 packets accept
        ip saddr @bannis drop

        counter comment "compteur des paquets rejetes"
        log prefix "NFT-INPUT-DROP " level info flags all
    }

    chain traversee {
        type filter hook forward priority filter; policy drop;

        ct state established,related accept
        ct state invalid drop

        # LAN -> Internet : uniquement via le proxy, plus DNS interne
        iifname "eth1" ip saddr 192.168.10.50 oifname "eth0" tcp dport { 80, 443 } accept
        iifname "eth1" ip daddr 192.168.30.10 udp dport 53 accept

        # Internet -> DMZ : services publiés (après DNAT)
        iifname "eth0" oifname "eth2" ip daddr 192.168.30.20 tcp dport @services_pub accept

        # DMZ -> LAN : interdit (regle d'or de la DMZ)
        iifname "eth2" oifname "eth1" log prefix "NFT-DMZ-TO-LAN " drop

        log prefix "NFT-FORWARD-DROP " level warn
    }

    chain sortie { type filter hook output priority filter; policy accept; }
}

table ip nat {
    chain prerouting {
        type nat hook prerouting priority dstnat;
        # Publication du serveur web de la DMZ
        iifname "eth0" tcp dport { 80, 443 } dnat to 192.168.30.20
    }
    chain postrouting {
        type nat hook postrouting priority srcnat;
        # Partage de l'acces Internet (adresse WAN dynamique)
        oifname "eth0" ip saddr @reseaux_lan masquerade
    }
}

Atouts distinctifs de nftables

  • Ensembles (sets) et maps : recherche à temps constant au lieu d'un parcours linéaire de milliers de règles.
  • Verdict maps : tcp dport vmap { 22 : accept, 80 : jump web, 25 : drop } — une seule règle remplace des dizaines.
  • Ensembles dynamiques à expiration : flags dynamic, timeout → bannissement automatique sans démon externe.
  • Une règle, plusieurs correspondances et une seule table inet pour IPv4+IPv6.
  • Rechargement atomique : pas de fenêtre où le pare-feu est ouvert.
  • Flowtable : déchargement du suivi de flux pour un routage rapide.
  • Compteurs, quotas, limitation de débit intégrés.

Verdicts et actions

  • accept — accepter et sortir de la chaîne
  • drop — jeter silencieusement
  • reject with icmpx type admin-prohibited — refuser en informant
  • jump <chaîne> / goto — chaîne utilisateur (goto ne revient pas)
  • continue, return
  • log prefix "…" level warn, counter, limit rate, queue (vers l'espace utilisateur)
  • dnat to, snat to, masquerade, redirect to :3128
Erreurs classiques en TP/examen
  • Oublier ct state established,related accept → la connexion s'établit mais rien ne revient.
  • Confondre INPUT (trafic pour la passerelle) et FORWARD (trafic traversant) : une règle de publication de service se met en FORWARD, pas en INPUT.
  • Oublier net.ipv4.ip_forward=1 : aucune règle FORWARD ne servira.
  • Faire le DNAT en POSTROUTING (trop tard : la décision de routage est déjà prise).
  • Filtrer sur l'adresse publique en FORWARD alors que le DNAT a déjà réécrit la destination en adresse privée.
  • Se couper l'accès SSH en appliquant policy drop avant d'écrire la règle d'autorisation (d'où l'intérêt du chargement atomique par fichier).

« Le NAT, c'est de la sécurité » : faux (nuancé)
Le NAT apporte un effet de bord utile — les machines internes ne sont pas directement joignables depuis l'extérieur — mais :
  • ce n'est pas une politique de sécurité : il n'exprime aucune règle, ne journalise rien d'intelligible et ne filtre pas le trafic sortant ;
  • il est contourné par toute connexion initiée de l'intérieur (le canal usuel des logiciels malveillants et des C2) ;
  • il casse la traçabilité (plusieurs machines derrière une IP → l'imputabilité exige de journaliser les ports source et les horodatages), la fin-à-fin, IPsec/AH, SIP, FTP actif ;
  • la sécurité vient du pare-feu à états, pas du NAT. En IPv6, il n'y a normalement pas de NAT : c'est le filtrage qui protège.

Traversée de NAT : STUN, TURN, ICE (WebRTC/SIP), UPnP/NAT-PMP (à désactiver : n'importe quelle application interne peut s'ouvrir un port), NAT-T pour IPsec (UDP 4500).

5. Architectures d'interconnexion

5.1 Anatomie d'une passerelle d'interconnexion sécurisée

Une passerelle d'interconnexion (ANSSI parle de passerelle d'interconnexion sécurisée) est le point de contrôle entre deux réseaux de niveaux de confiance différents. Elle enchaîne, dans cet ordre logique :

  1. Un filtrage réseau amont (routeur filtrant / pare-feu externe) : anti-usurpation, listes de réputation, limitation de débit, protection anti-DDoS.
  2. Un pare-feu à états qui porte la politique de flux entre zones.
  3. Des relais applicatifs par protocole : proxy sortant, reverse proxy + WAF entrant, relais SMTP, résolveur DNS de coupure, passerelle de transfert de fichiers.
  4. Un dispositif de détection : IDS/IPS sur TAP ou en coupure, analyse antivirale, bac à sable.
  5. Une journalisation complète exportée vers un puits de logs hors zone.
  6. Une administration cloisonnée : réseau d'administration hors bande, bastion, comptes dédiés, MFA.
Principe du « double filtrage hétérogène »
Deux barrières successives, de technologies différentes, sur des plans différents (réseau puis applicatif) : une vulnérabilité de l'une ne doit pas suffire à traverser toute la passerelle. C'est le cœur de la défense en profondeur appliquée à l'interconnexion.

5.3 Interconnexion inter-sites : points de vigilance

  • Chiffrement : IPsec IKEv2 avec suites modernes (AES-GCM 256, SHA-2, DH ≥ groupe 14 ou courbes elliptiques), PFS activé, certificats plutôt que PSK, renouvellement de clés.
  • Le tunnel n'est pas une politique : filtrer à l'intérieur du tunnel (un site compromis ne doit pas avoir accès à tout l'autre site).
  • Routage : éviter les routes par défaut croisées ; contrôler les préfixes annoncés.
  • Interconnexion avec un tiers (partenaire, infogérant, cloud) : zone d'échange dédiée, flux nominatifs, contractualisation (PAS/PAQ), révocation rapide, journalisation des accès distants — c'est le risque écosystème d'EBIOS RM.
  • MTU/MSS : l'encapsulation réduit la MTU utile → tcp mss clamping pour éviter les blocages silencieux.

6. Système de journalisation : définitions, sources, formats

6.1 Définitions

Vocabulaire
  • Événement : fait observable survenu dans le SI (une connexion, une authentification, un refus de paquet).
  • Journal (log) : enregistrement horodaté et structuré d'un événement.
  • Trace : ensemble de journaux permettant de reconstituer une activité.
  • Imputabilité : capacité à rattacher une action à une personne ou un système identifié — c'est l'objectif de la journalisation.
  • Preuve : journal dont l'intégrité, l'horodatage et la chaîne de conservation permettent de le produire en justice.

Pourquoi journaliser ? (les cinq finalités à citer) : 1) détecter (alimenter la supervision et le SIEM), 2) investiguer et reconstituer après incident (forensic), 3) prouver et imputer (obligations légales, contentieux), 4) se conformer (LCEN, RGPD, NIS 2, PCI-DSS, ISO 27001 A.8.15), 5) exploiter (diagnostic, capacité, qualité de service).

La correspondance qui sauve une investigation
Pour identifier « qui » se cache derrière une adresse IP à un instant donné, il faut croiser : bail DHCP (IP↔MAC↔heure) + accounting RADIUS / 802.1X (MAC↔identité↔port) + journal du NAT (IP privée+port↔IP publique) + journal du proxy (identité↔URL). Si une seule de ces sources manque ou n'est pas horodatée de façon cohérente, la chaîne d'imputabilité est rompue.

UDP 514 : le piège classique
Le syslog historique utilise UDP 514 : sans accusé de réception (les journaux se perdent silencieusement en cas de congestion), sans authentification (n'importe qui peut injecter de faux journaux), sans chiffrement (les journaux transitent en clair). Pour une passerelle, exiger TCP + TLS (6514) ou RELP, avec authentification mutuelle par certificat.

7. Politique de journalisation et agrégation

7.1 La politique de journalisation

C'est un document qui répond, source par source, aux questions : quoi journaliser, où, combien de temps, qui y accède, comment on protège et comment on exploite.

AxeExigences
PérimètreListe des sources et des événements, par niveau de criticité. Journaliser tout est aussi inefficace que ne rien journaliser : on cible les événements de sécurité (authentification, privilèges, accès aux données, changements de configuration, flux refusés, démarrage/arrêt des services de journalisation).
HorodatageSynchronisation NTP de toutes les sources sur une référence commune, expression en UTC (ou avec fuseau explicite), précision à la seconde au minimum. Sans cela, aucune corrélation.
Contenu minimalHorodatage, source, identité (utilisateur/machine), action, objet, résultat (succès/échec), adresses IP et ports (source et destination).
ConservationJournaux techniques : couramment 6 mois à 1 an en ligne (recommandation ANSSI usuelle : 6 mois minimum, 1 an fréquemment retenu), archivage plus long si obligation. Données de connexion d'un accès Internet : 1 an (cadre LCEN/CPCE). Durée justifiée et documentée au titre du RGPD.
IntégritéExport en temps réel vers un puits hors de la portée de l'administrateur de la source, support WORM ou stockage immuable, signature/hachage, contrôle d'accès strict.
ConfidentialitéLes journaux contiennent des données personnelles : accès restreint et tracé, pseudonymisation si possible, information des personnes, registre RGPD, durée limitée.
DisponibilitéDimensionnement (volumétrie en EPS et en Go/jour), files d'attente, redondance du collecteur, supervision de l'absence de journaux (un silence est une alerte).
ExploitationRègles de corrélation, cas d'usage, procédures d'astreinte, revue périodique, tests.
Premier réflexe d'un attaquant : effacer les journaux
D'où trois exigences non négociables : déport immédiat des journaux vers un serveur dédié (l'attaquant qui compromet le serveur ne peut plus effacer ce qui est déjà parti), flux unidirectionnel vers le puits (le collecteur n'ouvre pas de session vers les sources), compte d'accès distinct de l'administration du système supervisé. Événement à surveiller en priorité : Windows 1102 / arrêt du service rsyslog.

7.2 Agrégation, normalisation, corrélation

Notions

  • Agrégation : regrouper les journaux de sources multiples en un point unique.
  • Normalisation / parsing : convertir des formats hétérogènes vers un schéma commun (ECS, CIM, OCSF) — src_ip, user.name, event.action…
  • Enrichissement : ajouter contexte (géolocalisation, réputation, criticité de l'actif, propriétaire, identité).
  • Déduplication / agrégation d'événements : « 5 000 refus identiques » → 1 alerte avec un compteur.
  • Corrélation : croiser plusieurs sources dans une fenêtre de temps (échecs d'authentification puis succès puis création de compte = alerte).
  • Rétention chaude / tiède / froide : recherche rapide vs archivage économique.

Solutions et écosystème

  • SIEM : Splunk, QRadar, Sentinel, Elastic Security, Wazuh, Graylog, OpenSearch, Sekoia.
  • Pile ELK : Beats/Logstash → Elasticsearch → Kibana.
  • SOAR : orchestration et automatisation de la réponse.
  • EDR / XDR / NDR : détection sur le poste / multi-sources / réseau.
  • Référentiel de détection : MITRE ATT&CK (tactiques, techniques), règles Sigma (format portable), Yara.
  • SOC : N1 tri, N2 investigation, N3 chasse (threat hunting) et ingénierie de détection ; indicateurs : MTTD, MTTR, taux de faux positifs.

7.3 Cas d'usage de détection (exemples à savoir citer)

  • Force brute : N échecs d'authentification puis un succès depuis la même source.
  • Voyage impossible : deux connexions du même compte depuis deux pays en quelques minutes.
  • Balayage : une source contacte de nombreux ports/hôtes en peu de temps (visible en NetFlow).
  • Exfiltration : volume sortant anormal, ou nombreuses requêtes DNS avec des sous-domaines longs et aléatoires (tunnel DNS).
  • Balise C2 (beaconing) : connexions régulières à intervalle quasi constant vers une même destination.
  • Latéralisation : connexions SMB/RDP/WinRM inhabituelles entre postes.
  • Effacement de traces : arrêt du service de journalisation, purge du journal de sécurité.
  • Élévation : ajout d'un compte à un groupe privilégié hors fenêtre de changement.

8. NetFlow, IPFIX et sFlow

8.1 Le principe des flux

Qu'est-ce qu'un flux ?
Une séquence unidirectionnelle de paquets partageant les mêmes attributs pendant un intervalle de temps. Clé classique de NetFlow v5 (7 champs) : IP source, IP destination, port source, port destination, protocole IP, champ ToS, interface d'entrée. L'exportateur agrège les paquets en enregistrements de flux et exporte des métadonnées — pas le contenu.

Architecture : exportateur (routeur, pare-feu, sonde softflowd/pmacct) → collecteur (nfcapd, ntopng, Elastiflow) → analyseur (nfdump/NfSen, SiLK, Kibana).

Minuteries : active timeout (un flux long est exporté périodiquement, souvent 1 à 30 min) et inactive/idle timeout (flux clos après un silence, ~15 s). Elles expliquent le décalage entre l'instant réel et l'apparition dans le collecteur.

8.2 NetFlow pour la sécurité

Ce que les flux permettent de détecter

  • Balayages : une source, beaucoup de destinations ou de ports, flux très courts et sans réponse.
  • DDoS : explosion du nombre de flux/paquets vers une même cible.
  • Exfiltration : asymétrie inhabituelle (volume sortant >> entrant) vers une destination rare.
  • Beaconing C2 : périodicité régulière des flux vers une même IP.
  • Machines qui parlent à qui elles ne devraient pas : contrôle de la politique de cloisonnement a posteriori.
  • Cartographie et capacité : top talkers, matrices de flux réelles (base indispensable avant une micro-segmentation).

Limites

  • Pas de contenu : on ne sait pas ce qui a été transféré (impossible d'extraire un fichier ou une signature).
  • Échantillonnage : à 1/1000, les petits flux — souvent ceux d'un attaquant discret — peuvent disparaître.
  • Décalage temporel dû aux minuteries.
  • Charge sur le routeur exportateur ; export en UDP non authentifié (peut être forgé) → réseau de gestion dédié.
  • Le NAT en amont écrase les adresses réelles si le NAT n'est pas journalisé.
Flux vs capture complète (full packet capture)
NetFlow : très faible volume (≈1 à 2 % du trafic), conservation longue (mois), vision de tout le réseau, aucune atteinte au contenu (meilleure acceptabilité RGPD). PCAP : contenu intégral, indispensable au forensic fin, mais volume énorme, conservation courte (heures/jours) et périmètre limité. Les deux sont complémentaires : le flux dit où regarder, la capture dit ce qui s'est passé. 
# Collecte et analyse avec nfdump
nfcapd -w -D -l /var/cache/nfdump -p 2055        # collecteur, port UDP 2055
nfdump -R /var/cache/nfdump -s srcip/bytes -n 10 # top 10 des emetteurs
nfdump -R /var/cache/nfdump 'dst port 53 and bytes > 5000'   # suspicion de tunnel DNS

9. Filtrage applicatif (1) : le proxy

9.1 Principe et typologie

Proxy (mandataire)
Un relais applicatif qui rompt la connexion de bout en bout : il termine la session du client, analyse la requête, puis en établit une nouvelle vers le serveur. Il « comprend » le protocole, ce qu'un pare-feu à états ne fait pas.
AxeVariantesConséquences
SensDirect (forward) : protège les clients internes qui sortent · Inverse (reverse) : protège les serveurs publiésDeux fonctions distinctes, souvent deux machines distinctes
VisibilitéExplicite : configuré dans le navigateur ou par PAC/WPAD · Transparent/interceptant : le trafic est redirigé par le pare-feu (redirect to :3128) sans configuration du posteL'explicite permet l'authentification et évite les contournements ; le transparent est déployable sans toucher aux postes mais gère mal HTTPS
ProtocoleHTTP(S), FTP, SMTP (relais), DNS (résolveur de coupure), SOCKS (générique L5), SSHUn relais par protocole = surface d'attaque maîtrisée

9.2 Fonctions de sécurité d'un proxy sortant

  • Authentification des utilisateurs (Basic, NTLM, Kerberos/Negotiate, LDAP) → journalisation nominative des accès Internet : c'est la brique d'imputabilité.
  • Filtrage d'URL et de catégories (listes de l'université de Toulouse, éditeurs commerciaux), listes noires/blanches, filtrage par réputation.
  • Contrôle du protocole : seules les méthodes HTTP attendues, taille des en-têtes, blocage des CONNECT vers des ports non standard (contournement par tunnel).
  • Analyse antivirale via ICAP (RFC 3507) vers un service d'analyse (c-icap + ClamAV, éditeur commercial), et bac à sable pour les fichiers inconnus.
  • Journalisation : date, utilisateur, IP source, URL, méthode, code de retour, volume, catégorie, verdict.
  • Cache et limitation de bande passante (bénéfice historique, marginal aujourd'hui avec HTTPS).
  • Rupture protocolaire : aucun flux direct entre le poste interne et Internet — c'est ce qui bloque un grand nombre de canaux de commande et contrôle.

9.3 L'interception TLS (SSL bump / inspection)

Plus de 90 % du trafic web étant chiffré, un proxy « aveugle » ne voit que le nom de domaine (via le SNI) et l'adresse IP. Pour analyser le contenu, on procède à un MITM légitime : le proxy présente un certificat émis par une AC interne déployée sur tous les postes.

Ce que cela apporte

  • Analyse antivirale et DLP du contenu réel.
  • Filtrage d'URL complet (pas seulement le domaine).
  • Détection de canaux de commande et contrôle chiffrés.

Ce que cela coûte

  • Juridique : interception de correspondances → charte, information des utilisateurs, exclusion obligatoire des catégories sensibles (banque, santé, RH, syndicats), avis du DPO.
  • Technique : incompatible avec l'épinglage de certificat (HPKP, applications mobiles, mises à jour) ; risque de dégrader la sécurité TLS si le proxy valide mal les certificats amont.
  • Risque concentré : l'équipement voit tout en clair et détient une AC de confiance → cible de très grande valeur.
  • ECH / DoH : le chiffrement du SNI et le DNS sur HTTPS suppriment aussi la visibilité résiduelle → imposer un résolveur interne et bloquer les résolveurs DoH publics.

9.4 Le reverse proxy

  • Point d'entrée unique des services publiés : masque l'architecture interne (adresses, technologies, en-têtes Server, X-Powered-By).
  • Terminaison TLS centralisée : gestion des certificats, HSTS, suites cryptographiques modernes, OCSP stapling.
  • Répartition de charge et haute disponibilité (round-robin, moindre connexion, persistance de session), contrôles de santé.
  • Réécriture d'URL et d'en-têtes, X-Forwarded-For (attention : à ne pas faire confiance en aveugle côté applicatif).
  • Limitation de débit, mise en cache, compression, protection contre le slowloris.
  • Produits : nginx, HAProxy, Apache mod_proxy, Traefik, Envoy.
Question type
« Un reverse proxy est-il un WAF ? » — Non. Le reverse proxy relaie, termine TLS et répartit ; il ne comprend pas les attaques applicatives. Le WAF est le module d'analyse qui s'ajoute (souvent sur le reverse proxy, par exemple ModSecurity dans nginx).

10. Filtrage applicatif (2) : le WAF

10.1 Rôle et modèles de sécurité

WAF (Web Application Firewall)
Pare-feu spécialisé HTTP(S), placé devant une application web, qui inspecte requêtes et réponses pour détecter et bloquer les attaques applicatives. Il opère là où un pare-feu réseau est aveugle : le port 443 est « ouvert », c'est le contenu qui est malveillant.
ModèlePrincipeAvantagesInconvénients
Négatif (liste noire / signatures)On décrit ce qui est interditDéploiement rapide, génériqueContournable (encodage, obfuscation) ; ne voit pas les attaques métier
Positif (liste blanche)On décrit précisément ce qui est autorisé (paramètres, types, longueurs)Très robuste, bloque l'inconnuCoûteux à établir et à maintenir ; nécessite une phase d'apprentissage
Hybride / scoringChaque anomalie ajoute des points ; on bloque au-delà d'un seuilCompromis réaliste — c'est le modèle du OWASP CRSRéglage du seuil et des niveaux de paranoïa

10.2 ModSecurity et l'OWASP Core Rule Set

  • ModSecurity : moteur de règles (Apache, nginx, IIS ; successeur : Coraza). Modes : SecRuleEngine On (bloquant), DetectionOnly (journalise sans bloquer — toujours commencer par là), Off.
  • Phases de traitement : 1 en-têtes de requête, 2 corps de requête, 3 en-têtes de réponse, 4 corps de réponse, 5 journalisation.
  • OWASP CRS : jeu de règles générique. Niveaux de paranoïa (PL1 à PL4) : plus le niveau est élevé, plus la détection est stricte… et plus les faux positifs augmentent. Notation d'anomalie : seuils par défaut 5 en entrée / 4 en sortie ; les règles ajoutent 5 (critique), 4 (erreur), 3 (avertissement), 2 (notice).
  • Réglage : exclusions ciblées par règle/paramètre/URL plutôt que désactivation globale ; itérer en mode détection sur du trafic réel avant de bloquer.

Limites et contournements du WAF
Encodages multiples (URL, double URL, unicode, hexadécimal), HPP (pollution de paramètres), fragmentation via Transfer-Encoding: chunked, requêtes surdimensionnées dépassant la limite d'inspection du corps, verbes HTTP inhabituels, HTTP request smuggling (désynchronisation entre le proxy et le serveur), accès direct au serveur en contournant le reverse proxy (adresse IP d'origine exposée). 11. Fiche mémo express

Netfilter / nftables

  • 5 hooks : prerouting, input, forward, output, postrouting
  • DNAT → prerouting · SNAT/masquerade → postrouting
  • Familles : ip, ip6, inet, arp, bridge, netdev
  • Types de chaîne : filter, nat, route
  • Priorités : raw −300, mangle −150, dstnat −100, filter 0, srcnat 100
  • États : new, established, related, invalid, untracked
  • Toujours : ct state established,related accept + ct state invalid drop + policy drop

Journalisation

  • PRI = facility × 8 + severity ; sévérité 0 = emerg … 7 = debug
  • RFC 3164 (BSD) vs RFC 5424 (ISO 8601, structured data)
  • UDP 514 (non fiable) · TCP 514 · TLS 6514 · RELP
  • Conservation courante 6 mois – 1 an ; données de connexion 1 an
  • Déport immédiat + horodatage NTP/UTC + intégrité + accès restreint
  • L'absence de journaux est une alerte

NetFlow

  • Flux = séquence unidirectionnelle, clé v5 sur 7 champs
  • v5 fixe / v9 à modèles / IPFIX standard / sFlow échantillonné
  • Exportateur → collecteur → analyseur ; port usuel UDP 2055
  • Métadonnées uniquement : pas de contenu
  • Détecte : balayage, DDoS, exfiltration, beaconing

Applicatif

  • Proxy direct = sortants (imputabilité) ; reverse proxy = entrants (publication)
  • Explicite (PAC/WPAD) vs transparent (redirect)
  • ICAP = analyse antivirale déportée
  • WAF : modèle négatif / positif / scoring (OWASP CRS, PL1–PL4)
  • Toujours démarrer un WAF en DetectionOnly
  • Le WAF ne remplace pas le code sécurisé
Plan type « concevez une passerelle d'interconnexion sécurisée »
1) Identifier les zones et le sens des flux → 2) écrire la matrice de flux (source, destination, protocole, port, justification) → 3) pare-feu à états en interdiction par défaut, avec règles nommées et journalisées → 4) NAT si nécessaire, journalisé (ports source) → 5) relais applicatifs : proxy sortant authentifiant, reverse proxy + WAF entrants, relais SMTP/DNS → 6) détection : IDS/IPS, NetFlow, antivirus → 7) journalisation centralisée en TLS vers un puits hors zone, horodatage NTP, conservation définie → 8) administration cloisonnée (bastion, hors bande, MFA) → 9) haute disponibilité et sauvegarde des configurations → 10) exploitation : revue des règles, tests, mise à jour, procédures d'incident.
